# Task completion failure inventory

Written before implementation/isolation code for this issue. No owner data is modified. Root's read-only installed diagnosis found tracked tasks without child chats/turn counts and terminal tasks with unupdated plan entries; a successful reply alone cannot prove all work complete.

- `start_task` saves only an origin chat, losing the exact producing run. A later unrelated successful reply must not close that old task; absent legacy linkage is unknown, never guessed from title/time/latest run.
- A new tracked task whose exact owning turn successfully finalizes a nonempty result and a completed/skipped plan remains running if `finish_task` was omitted. Applied owner steers have distinct runs but share the finalizing turn; those exact identities must settle correctly.
- An intermediate successful turn, partial result, open approval/question, pending sibling/steer, engine retry, goal pause, stop, cancellation, failure, empty response, or pending finalizer must not declare the task or its dependencies complete.
- A final background result with an unupdated plan causes repeated full work turns, potentially repeating external operations and ultimately failing after six turns. Preserve a nonurgent versioned result candidate instead; it must not become a new question/Needs-you obligation or silently unblock dependencies.
- Explicit `finish_task done` is authoritative closure, but individual pending/active checklist rows were not separately updated. Preserve their original states/notes and present them truthfully; do not turn them into invented done/skipped assertions.
- A result candidate can be acknowledged complete or continued only for its exact saved version and exact settled producing run. Wrong key/ID/version, new plan/question/result, new active/pending work, queued/applied steering, goal pause, or owner cancellation must refuse stale resolution.
- Complete must retain result/history, allow prerequisites only after genuine acknowledgment, and never replay the work. Continue must use the same task/chat and retain original deliverables/plan, clearing the old receipt; a late old finalizer cannot restore a stale candidate.
- Repeated native finalization/restart must remain idempotent and must not duplicate task reports or work admission. Missing/deleted legacy producer identities must fail closed without breaking normal task reads.
- Runtime/SQLite/protocol fixtures must block external IO, use only synthetic runner metadata/claims, preserve interrupted/paused cases, exercise native finalization and scheduler persistence, produce a JSON record, and normally tear down their isolated homes. No paid engine/provider/account work, personal data mutation, unit tests or shared build.

Independent-review regression cases: Heartbeat must not arm a questionless result receipt; unversioned/lost-ack `resume_task` must not replay a later candidate; a tool admitted before finalization must not overwrite the owner-resolved/newer task; media-only or missing attachment references must not cause blind generation repeats. Result-ready delivery must still reach the originating agent once, with honest unconfirmed-checklist wording, and stale unadmitted reports must remain superseded. Applied-steer ownership and literal native Stop are exercised separately. Permanent native completion journeys are maintained in `artifacts/task-presence/run.mjs`; broader verification guidance is in `docs/regression-checks.md`.
