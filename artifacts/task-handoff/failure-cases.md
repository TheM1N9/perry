# Owner-visible task relay inventory

The original `run.ts` records fourteen relay failure modes before its checks. This extension adds the following before isolation changes. Use a production build, disposable native Temp home, real runner/MCP, fake ACP engine, loopback Telegram stand-in and real browser. Never run the legacy live Convex/Codex goals/background-task scripts.

15. Startup warms/downloads a real embedding model or routes a failure through another installed/signed-in provider. Seed a bounded fixture embedder, deny external fetches, isolate native account homes and refuse non-fake ready engines before task work.
16. The backend relay receipt says answered but the originating owner cannot see the result in their actual browser, or the current contenteditable composer cannot start/resume it. Verify real owner input and visible results, with browser errors recorded.
17. Cancellation while queued/preparing loses to a delayed brain callback, tool result, finalizer or server/runner restart; cancelled work is resurrected or a completed notice reaches the parent anyway.
18. A blocked task's answer loses its existing chat/plan or resumes twice. A stale decision control answers a later question; a guest/other chat can claim the result.
19. Restart between child completion and parent relay loses or duplicates the result, changes the origin or repeats an already answered handoff. Preserve exact task/turn/run identities and source provenance.
20. A blocked report delayed until after the owner has already answered elsewhere tells the parent to ask the obsolete question again. Distinguish historical snapshots from current actionable decisions.
21. Dependency or goal transitions queue a second child turn, let dependent work run before prerequisites or lose the verified prerequisite result. Prefer existing safe lifecycle coverage; only add a browser case when it proves a distinct owner-visible contract.
22. Fixture output interprets native streaming drafts or a fake's parsing mismatch as a product delivery bug. Record real messages/turns/tool responses and preserve once-only final-answer assertions.
23. Failure leaves polling sockets, browser/server/runner/fake children or native Temp data alive. Stop all owned processes and the Telegram listener in a finalizer; never retry a previously policy-rejected cleanup path.

Record actual failure state and repeatable JSON output. Do not weaken source isolation, single-answer, provenance or completed-result assertions when migrating a stale fixture.
