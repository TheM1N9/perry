# Saved credentials at rest (#251)

Perry encrypts the `value` field in `vault` and `secrets` with native Node AES-256-GCM. Every write has a fresh 96-bit IV and 128-bit authentication tag. The envelope is `perry:credential:v1:<iv hex>:<tag hex>:<ciphertext hex>`, with the version and table authenticated as additional data. The schema stays a string. No Whirl code was copied or adapted and no dependency was added.

The setup integration generates a 256-bit `PERRY_CREDENTIAL_KEY` alongside `DASHBOARD_KEY` in `.env.local` for a fresh installation. On first backend startup, `initializeCredentialEncryption(sql, HOME)` loads or creates `HOME/credential-key` with exclusive creation, mode 0600 and fsync. Upgrading an existing install creates that file directly without rewriting `.env.local`. The environment override must be exactly 64 hex characters and must match an existing key file. Key creation occurs before encryption; an existing encrypted row, migration marker or encrypted backup prevents automatic replacement of a missing key. No key is derived from the dashboard key, so dashboard authentication key changes do not invalidate stored credentials.

Keep the credential key in a secure, separate recovery location. Database/backup copies alone cannot unlock the saved values. A copy of all of Perry's home, including the key file, can unlock them. POSIX mode 0600 applies where supported; Windows inherits the user's directory ACL. This protects copied database and backup files, not access by the same signed-in OS user or historical filesystem snapshots, deleted-file recovery, third-party sync/version history, disk forensic recovery, or backups already taken elsewhere.

## Reads and writes

`vault.save` and `secrets.set` encrypt values before writing. `vault.reveal`, `savedValues`, `keptSecrets`, service resolution and the last-four preview decrypt for their existing server consumers. Metadata-only lists do not decrypt. Empty stored service values still fall back to environment keys. Redaction continues comparing real plaintext values and never ciphertext. The SQLite Store also protects inserts/replacements/patches, covering both Runtime document import and Convex archive import. Raw Store exports and SQLite snapshots contain encrypted values. Authenticated ciphertext can be imported/restored only with the original key; a different install's ciphertext fails instead of becoming a credential.

The prefix is reserved in persisted data. New user-entered values beginning with it are safely encrypted as literal values. A pre-upgrade plaintext credential beginning with `perry:credential:` is ambiguous and stops migration for manual recovery instead of being silently changed. Authentication binds ciphertext to its table, not its row: this is confidentiality for copied storage, not protection against an attacker who can rewrite arbitrary rows on the machine.

## Migration, backups and recovery

The server/index.ts bootstrap runs synchronously before constructing/publishing the Runtime. It migrates SQLite and every existing supported backup before requests/background jobs are accepted. The Store repeats the live migration defensively for alternative entry points. Missing keys never cause fallback to plaintext or environment credentials over an encrypted stored row.

A SQLite transaction validates existing envelopes and encrypts all legacy rows, preserving IDs, metadata, and empty values. It records an authenticated key check plus a pending cleanup flag. Secure deletion, WAL checkpoint with TRUNCATE, VACUUM and another checkpoint remove legacy bytes from the active SQLite files. The cleanup flag becomes complete only afterward. A crash after commit retries physical cleanup on the next startup. Bad data/wrong keys roll back row changes. Disk-full/lock/cleanup failures stop startup; do not serve requests after catching them.

Existing `.sqlite`/`.db` backups migrate in place with the same transaction and cleanup procedure. JSON backups keep their shape: credential arrays named `vault` and `secrets`, including under a `tables` wrapper, have each `value` encrypted; other historical Brain/persona/journal fields are preserved. JSON replacement uses an encrypted-only temporary file, fsync, then rename. Symlinks, unsupported file extensions and invalid formats stop startup for review. SQLite sidecars are handled with their parent database. A failure between backup files may leave some backups already encrypted, but each original remains recoverable with the same key; retry is idempotent. Do not remove the key or downgrade in response to a partial migration.

JSON staging files have the exact shape `<original.json>.perry-credential-<32 hexadecimal characters>.tmp` in the original's directory. Perry closes the staging descriptor before rename and attempts guarded cleanup if writing, fsync, closing or renaming fails, preserving the original. An interruption can leave a partial or complete staging file. On the next startup, Perry validates that both paths are regular files, the matching original is parseable JSON and any credential envelopes in it authenticate with the loaded key. It then discards staging and retries encryption from the original; staging is never promoted, even if complete. This recovery also works when the original was already encrypted before the interruption.

If the original is missing, is a link/directory, is malformed, or has invalid credential envelopes, automatic recovery stops and preserves staging for manual review. A failure to remove staging also stops startup; retry after fixing the filesystem problem. Unknown temporary names, staging directories, and the older ambiguous `<original.json>.<16 hex>.json` names are never automatically deleted. For an old ambiguous leftover, review the original and leftover separately while Perry is stopped; move only the confirmed incomplete duplicate out of `backups` before retrying. Never discard the only remaining copy or the credential key.

Future full SQLite snapshots (`server/brainIndex.ts` VACUUM INTO) and raw document exports already contain encrypted rows. Historical JSON Brain migrations do not export credential tables. `scripts/migrate.ts` reads legacy Convex export zip files through `server/importer.ts`; Store inserts encrypt the imported values. The original user-supplied/Convex-generated zip, outside `HOME/backups`, is not rewritten. Treat that source archive as sensitive and remove it or secure it separately when it is no longer needed. Unsupported archives placed inside `HOME/backups` block migration for explicit review.

Restore a migrated SQLite backup as the live database with the original key file/environment available, then start this version of Perry. JSON credential rows can be restored through normal document import with the same key. Keep both `.env.local` and `credential-key` consistent if both hold the key. If the key is lost permanently, saved encrypted credentials cannot be recovered; restoring the key is the only automatic recovery. Re-entering credentials requires a deliberate fresh store/recovery operation; no destructive reset is performed here.

Downgrading to a version without encryption support would send envelope strings to credential consumers. Restore a pre-encryption backup and the older application together only if deliberately rolling back to plaintext storage. There is no automatic decrypt-to-plaintext rollback or key rotation; rotating a key requires reencrypting live data and every retained backup together.

## Verification

Failure inventory was written before isolated verification code in `artifacts/secrets-at-rest/failure-cases.md`. Run the fake-data backend E2E from the repository root:

```powershell
pnpm exec node --experimental-transform-types --import ./artifacts/secrets-at-rest/node-loader.mjs artifacts/secrets-at-rest/run.ts
```

Node 25 supports native TypeScript transformation and SQLite; the loader only resolves the project's extensionless imports and writes no compiled output. Bun 1.3.8 cannot resolve `node:sqlite`, so it cannot run this harness. The test sets synthetic `PERRY_HOME`, `DASHBOARD_KEY`, and fake engine selection before any project imports. It exercises actual Runtime transactions, validators, schema, vault/service handlers, migration, backup restore, restart, redaction and raw-byte scans without a network listener, model calls, or installed Perry access. Its disposable database/key fixtures are removed and only boolean results remain in `.batch-work/batch-1/251/e2e-result.json`. Combined build and application E2E evidence is in artifacts/batch-1/.

The staging recovery follow-up adds actual Node filesystem write/fsync/unlink fault injection scoped to the exact disposable staging path, plus partial/complete interruption fixtures and preservation cases. Native filesystem exports are restored before subsequent scenarios. All 19 scenarios passed after the follow-up; no production failure toggles were added.
